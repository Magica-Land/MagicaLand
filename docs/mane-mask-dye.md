## 开发者速览

核心是把“纹理明暗”和“这一块染什么颜色”拆开。`mane.png` 继续保存灰度纹理和手绘明暗；各款式 JSON 按 UV 像素指定色区编号。渲染时读当前部件、款式的色区，找到玩家选择的颜色，再套用原灰度对应的色阶。因此换挑染不需要给模型叠一层几何，也不会丢掉发丝纹理。

02–08 的后续修订已改为沿发块/发束方向延续的六区，01 不变。源分区坐标在 `Resources/ManeDyes/flow-layout.json`，可用 `node tools/generate-mane-dye-masks.mjs --check` 核对，显式 `--write` 同步导出。主卷传递全宽色序，碎发继承子区间；相关 UV 微调和纹理保护见 `docs/mane-shared-texture-repair.md`。下方早期验证数字为当时记录，当前资源以重新生成检查为准。

| 文件/模块 | 职责 |
| --- | --- |
| `mane_dyes/stripe01.json` | 只描述 01 的色区形状，1–6 是编号，不是 RGB 或阴影强度 |
| `mane_dyes/style02.json` … `style08.json` | 各自描述对应款式的色区；同一文件只列实际存在的 FRONT / BACK / TAIL |
| `ManeDyeMask` | 校验并展开 JSON 遮罩，兼容旧版编号，按纹理尺寸取样 |
| `ModelConfig` | 保存每部件的 6 色；null 表示锁定跟随该部件主色，并迁移旧配置 |
| `ManeDye` + `ManePalette` / `BodyColorRamp` | 解析主色联动和色区锁，为独立颜色计算阴影/高光，保持原 alpha |
| `ManeTintTextures` | 合成并缓存动态纹理；遮罩身份、部件和色阶共同决定分色缓存，资源重载/退出时回收 |
| `ManePage` / `PonyRenderer` | 折叠式颜色控件；选择部件纹理并跳过旧挑染覆盖骨骼 |

例如后发 4 区设粉色、5 区设紫色，其余色槽为 null：4、5 区用自己的色阶，其余完整继承后发主色及其手动/自动明暗。前后发和尾巴各有自己的数组，颜色保存和联机同步仍走现有整对象 JSON，不需要新增服务端消息类型。

维护时主要注意：

- 改形状改遮罩，改质感改基础贴图；不要用明暗像素值反推色区，否则阴影会被误分成挑染。
- 改 UV 后必须同步该款式遮罩。新增发型时需要配套遮罩、注册表和 `ManeDye` 支持范围，不能只改 JSON 的描述字段。
- 不同款式可以复用基础贴图与 UV；它们各自的遮罩和动态纹理独立。同款同部件内完全重叠的 UV 仍只能得到相同颜色，若两处应有不同分区，必须先拆开这项 UV 冲突。
- 锁定色区必须继承完整色阶，而不只是同一个主色 RGB，否则主色手动调阴影时仍会露出分界。
- `Resources` 中的贴图/模型与 `appearance/src/main/resources` 中的运行时版本要一起维护；Blockbench 不会执行 Java 调色代码，玩家分色不应烘焙回基础贴图。

独立逻辑测试：`./tests/mane/run-dye-tests.ps1 -GsonJar '本机现有 gson.jar 的绝对路径'`。需要 JDK 17+，仅编译测试到临时目录，不运行 Gradle。

## 使用

捏马 → 编辑角色 → 鬃毛与尾巴 → 遮罩分区调色。开启后，在对应部件主色下展开“前发分色 / 后发分色 / 尾巴分色”。所有已列出的款式均使用自己的六区遮罩，前发、后发和尾巴可混搭不同编号。

- 每区锁定时跟随本部件主色和完整高光/阴影；解锁保留当时颜色，然后可以独立调整。
- 相邻的 4、5 区可设置为粉、紫，其余区跟随主色，即可手动搭配双带挑染。全部区域解锁后可做多色搭配。
- 每个部件单独保存 6 色，不强制前发、后发、尾巴使用同一套色槽。部件主色之间原有联动锁保留；色区锁表示跟随本部件主色，而非跟随另一个部件的同编号色区。
- 色槽按部件保存，不是每个款式各保存一份：更换发型会沿用当前部件的 6 色，但色区位置由新款式遮罩决定。需要保存不同配色组合时使用已有角色预设。
- “全部色区跟随本部件主色”将当前部件的 6 色重新锁定；关闭总开关只停用分色，不清空配色。
- 不同于主色的独立色区自动计算明暗；本轮未增加逐色区的阴影/高光手动编辑。与主色相同的色区复用主色完整色阶，手动阴影时也不留分区边线。

默认不开启分区调色。原有挑染配置迁移时，前发/尾巴的旧挑染色放入 4、5 两区；后发 4 区继承主挑染色、5 区继承副挑染色。其余区域默认跟随主色，因此不会默认变成六色彩虹。

后发色带参考作者 `Resources/Textures/TS.png`，使用白模化前提交 `3fbe96f39e76c7dd717a7cb00ecb9b9aafdcfbb9` 中的旧 UV 恢复位置。为满足本次上移和铺满分区的要求，将原稿粉/紫像素的对应位置拟合为连续三维分区坐标，上移 1.25 个模型单位，再延展到相邻发片和厚度面。它不是上一轮原稿逐像素遮罩的原位复制，也不再局限于原稿中有挑染的少数面。

## 数据与兼容

遮罩使用 version 3、256×256 像素坐标，尺寸字段为 `texture_width` / `texture_height`。每个 region 包含 `part`、`channel`、`runs`。`part` 为 FRONT / BACK / TAIL；`channel` 为 1–6；每条 run 为 `[y,x0,x1]`，终点 x1 不包含。遮罩外为主色。

`stripe01.json` 内的 `preset` 为 `stripe01`；`style02.json` … `style08.json` 的 `preset` 分别为 `style02` … `style08`。读取时校验文件与身份一致，拒绝在 07 遮罩里定义后发或在 08 遮罩里定义尾巴。某份资源缺少一个合法部件时，该部件回退普通发色，不借用其他款式或部件的遮罩。

配置中的 `maneDyePreset` 保持 `stripe01`，表示继续使用现有分区模式；它不是当前实际资源文件名。`ManeDye.maskName(config, part)` 依据所选部件款式决定资源身份。旧配置无需改字段，网络协议也不增加。

每份资源限制 18 区、8192 条 run、1024×1024 尺寸和 256 KiB 大小；拒绝非法坐标、重复区域和同部件内重叠。01 仍支持旧 version 1 / 2 资源，旧通道 1 / 2 分别规范化为新色区 4 / 5；新增款式要求 version 3，避免误套旧通道含义。旧版客户端不能读取 version 3，联机双方应使用同版本。

新增 `frontManeDyeColors`、`backManeDyeColors`、`tailDyeColors` 三个长度为 6 的数组，null 色槽表示跟随主色。旧 `maneDyeColor` / `maneDyeAccentColor` 仅用于缺少数组时的一次迁移；有数组后以数组为准。非法色值回退为跟随主色，过长/过短数组规范化为 6 项。

保存、复制、联机继续使用现有 JSON 通道，不修改服务端转发协议。分色缓存键包含不可变的实际色阶列表、传统/色阶模式、部件和遮罩身份；即使 02 与 05 共用同一基础纹理和配色，也不能误用对方的分区结果。关闭分色或缺少遮罩时不将色槽、款式或部件加入普通发色缓存，同色仍能复用。每款遮罩单独缓存和记录失败，某款损坏不会使所有挑染停用；资源重载、断开连接或退出时清空这些记录。保留原 128 项 / 64 MiB 动态纹理缓存上限。

旧 `Style01FrontManeHighlight` 仍在源工程中保留回退资料，但游戏渲染跳过它。此规则只按该骨骼全名判断，不能把其他含 `Highlight` 的骨骼一并删除：`Style07FrontManeHighlight` 自身及其 `Style07FrontMane02` 子骨骼均包含有效发片。Blockbench 不执行玩家调色代码；不要把玩家色区配色涂进灰度源图。
